# PC-001 — Single Detection template as a one-member Production Replication

- Status: **IMPLEMENTED — VERIFIED (static)** (owner approved 2026-10-29; implemented 2026-10-29)
- Created: 2026-10-29
- Owner: Delaney Foley
- Related requirements: PR-013 (creation modes), PR-014 (Blank), PR-015 (Prompt Assist)
- Related decisions: PDEC-014–PDEC-022 (proposed below, from this conversation)
- Baseline source commit at planning time: `73e0049` (see state.md)

## Request

Make the former Blank Template and Prompt Assist single-prompt detection
templates behave as a *single-detection slice of Production Replication*. A
single-detection run should execute exactly like the production-context
aggregate, but over **one** detection: a shared preamble sourced from a selected
production context, followed by that one detection's block, with no system
prompt and no Decision Policy / Decision Rubric. "DETECTED" means the single
detection's label is returned by the model (presence semantics, as in the
aggregate). Rename the "User Prompt Addendum" authoring section to "Detection
Prompt". Collapse the two single-prompt creation modes (Blank, Prompt Assist)
into one "Single Detection" mode with an optional Prompt Assist generate button,
so the creation UI offers exactly two modes: **Single Detection** and
**Production Replication**. Remove the Admin category prompt editors and retire
their settings/keys; the user instead selects the context whose shared
instructions (preamble) the single detection runs inside.

## Confirmed decisions (this conversation)

- PDEC-014: Single Detection runs as `preamble + exactly one detection block`,
  reusing the aggregate inference path; the preamble comes from the selected
  production context. No sibling members are included.
- PDEC-015: Production Label is a **mandatory** field for a Single Detection; it
  is the label used in the detection block and the label whose presence means
  DETECTED. The context remains selectable even when the detection is not yet a
  member of that context.
- PDEC-016: Apply the new shape to the detection-creation form, the
  Development-mode execution/run panel, and the prompt-version editor.
- PDEC-017: Drop the `detection_category` selector (Incorrect Capture / Hazard
  Identification) from the Single Detection flow entirely.
- PDEC-018: Forward-only change. Existing saved detections/versions retain their
  stored `system_prompt`, `label_policy`, `decision_rubric`, and
  `user_prompt_addendum` values in the database; these fields are simply no
  longer surfaced/authored for new Single Detection work. No migration or
  backfill, no destructive cleanup of existing rows.
- PDEC-019: Collapse Blank + Prompt Assist into one "Single Detection" creation
  mode. The authoring field (Detection Prompt) starts blank; a "Generate with
  Prompt Assist" button optionally fills it. Creation modes become exactly
  **Single Detection** and **Production Replication**.
- PDEC-020: Remove the four Admin category prompt editors and retire their
  setting keys, API fields, and the `STRICT_JSON_CONTRACT` placement for the
  single-prompt path. Single Detection must run exactly like Production
  Replication (aggregate `{detections:[...]}` schema, label enum, no system
  prompt), not via the old strict single-object JSON contract.
- PDEC-021 (OI-1): A Single Detection version **freezes a production context
  snapshot** (as PRODUCTION_MODE does) for reproducible parity; the preamble is
  extracted from that frozen snapshot, not the live context.
- PDEC-022 (OI-3): Prompt Compare and Prompt Iteration are **fully reworked** to
  be functional with the single Detection Prompt model: they operate on the one
  editable Detection Prompt field (the member description), run candidates via
  the aggregate single-member inference path with presence semantics, and no
  longer read/produce `system_prompt`, `label_policy`, or `decision_rubric`.

## Desired outcome vs current behavior

**Current single-prompt (DEVELOPMENT_MODE):**
- System prompt from Admin category template
  (`incorrect_capture_system_prompt` / `hazard_identification_system_prompt`),
  sent as `systemInstruction`/`system` by each provider.
- User prompt = Admin category `user_prompt_template` (contains the task line and
  `STRICT_JSON_CONTRACT`) + `user_prompt_addendum` + `fixed_guidance` +
  Decision Policy (`label_policy`) + Decision Rubric (`decision_rubric`),
  assembled by `compileUserPrompt`.
- Output schema: single object `{detection_code, decision, confidence,
  evidence}` via `STRICT_JSON_CONTRACT`; decision is DETECTED/NOT_DETECTED.
- Two creation modes (Blank, Prompt Assist) plus Production Replication.
- Admin tab exposes four category prompt editors.

**Desired single-prompt (Single Detection):**
- No system prompt.
- Prompt = selected context preamble (shared instructions) +
  `compileAggregatePrompt(preamble, [{ label: productionLabel, description:
  detectionPrompt }])`. The "Detection Prompt" text is the member description.
- Output schema: aggregate `{detections:[{detection, reasoning}]}` with the
  label enum = `[productionLabel]`; DETECTED iff the label is present (reuse
  `deriveAggregateOutcome` presence semantics). No policy/rubric.
- One creation mode "Single Detection" (optional Prompt Assist button) +
  Production Replication.
- Admin category prompt editors removed.

## Proposed acceptance criteria

1. The creation UI shows exactly two modes: Single Detection and Production
   Replication. Single Detection shows a mandatory Production Label, a context
   selector, a "Detection Prompt" field, and a "Generate with Prompt Assist"
   button; it shows no System Prompt, Decision Policy, Decision Rubric, or
   detection-category selector.
2. Saving a Single Detection with a blank Production Label is blocked with a
   clear message.
3. A Single Detection run builds `preamble + one block` and calls the aggregate
   inference path; the compiled-prompt preview matches what runs. No system
   instruction is sent.
4. The run result is DETECTED iff the model emits the detection's label
   (presence), using the aggregate `{detections:[...]}` schema; NOT_DETECTED
   otherwise. Evidence is populated from the label's reasoning.
5. The Admin tab no longer renders the four category prompt editors, and
   `/api/admin/prompts` no longer reads/writes those keys.
6. Prompt Assist populates only the Detection Prompt field.
7. Existing saved detections/versions still load without error (legacy fields
   ignored, not deleted).
8. The Development-mode execution/run panel and prompt-version editor reflect the
   same removals and the Detection Prompt rename.
9. Prompt Compare synthesizes a single Detection Prompt from source versions'
   Detection Prompts and can run the synthesized version via the aggregate
   single-member path; no policy/rubric/system fields appear in its input/output.
10. Prompt Iteration generates, evaluates, and saves candidates as single
    Detection Prompt edits, running them through the aggregate single-member path
    with presence-based DETECTED semantics, and produces valid metrics.

## Migration / data-loss risk

- Forward-only (PDEC-018). Legacy columns/settings are retained; no row deletion
  or schema drop. Risk: old DEVELOPMENT_MODE versions created before this change
  may render/run differently; mitigated by OI-2 (keep enum) and by the run path
  detecting whether a composition exists. Reproducing an *old* single-prompt run
  exactly is not guaranteed and is an accepted deviation.

## Rollback

- Revert the PC-001 commit(s). Because the change is forward-only and does not
  drop columns or delete settings rows, reverting restores the prior UI/run
  behavior without data recovery steps. Retired Admin setting keys would need to
  be re-added to the settings schema on rollback (tracked here).

## Implementation record (2026-10-29)

Core model: a Single Detection is a `DEVELOPMENT_MODE` version that carries a
one-member `composition` (the target member) + a frozen `production_snapshot_id`
+ a mandatory `production_label`. A version "runs as an aggregate" iff it has a
composition + snapshot, so Single Detection and Production Replication share the
exact aggregate execution path; a Single Detection is simply the one-member case.

Files changed:
- `src/lib/productionMirror.ts` — added `buildSingleDetectionComposition`.
- `src/lib/useSingleDetection.ts` (new) — context select → freeze snapshot →
  preamble + mandatory label + Detection Prompt + compiled preview.
- `src/components/shared/SingleDetectionPanel.tsx` (new) — authoring UI.
- `src/components/DetectionSetup.tsx` — two creation modes (Single Detection +
  Production Replication) with an optional Prompt Assist button; mandatory
  Production Label; "Detection Prompt" rename; removed System Prompt / Decision
  Policy / Decision Rubric / category selector from the single-prompt flow; the
  version editor's Development branch now uses the Single Detection panel and
  saves a one-member composition. (Legacy single-object JSX is retained behind a
  `{false && …}` guard to avoid destabilizing the top-panel preview; it never
  renders.)
- `src/app/api/prompts/route.ts` — persists composition/snapshot/label for any
  composition-backed version (incl. DEVELOPMENT_MODE); no system prompt / no
  category-template baking when a composition is present; legacy fallback kept.
- `src/app/api/runs/route.ts` — builds the aggregate for any composition-backed
  version (presence semantics; DETECTED iff the label is returned).
- `src/lib/inference/index.ts` — `runDetectionInference` is now composition-aware
  (loads the frozen snapshot and runs via `runAggregateInference`), so Compare
  and Iteration evaluate Single Detection candidates through the aggregate path.
- `src/app/api/gemini/detection-assist/route.ts` + `src/lib/adminPrompts.ts` —
  Prompt Assist now generates a single `detection_prompt`; default assist
  template rewritten; `renderPromptAssistTemplate` drops the category arg.
- `src/components/AdminPrompts.tsx` + `src/app/api/admin/prompts/route.ts` —
  removed the four category prompt editors and retired their setting keys/API
  fields.
- Prompt Iteration (`candidateGen.ts`, `evaluation.ts`, `saving.ts`,
  `orchestrator.ts`, `types.ts`) — a `detection_prompt` candidate field is the
  single tunable lever for composition sources; `buildSingleDetectionPrompt`
  generation branch; `fallbackCandidates` single-detection variants; candidate
  evaluation + saving build/persist one-member composition-backed versions.
- Prompt Compare (`synthesize.ts`) — the synthesized version is persisted as a
  composition-backed Single Detection (member description = merged
  `detection_guidance`/`detection_prompt`) and evaluated via the aggregate path.
- `tests/singleDetection.test.ts` (new) — composition builder, iteration saving
  composition path, and single-detection fallback candidates.
